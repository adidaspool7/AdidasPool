\chapter{Detailed Database Schema}
\label{app:db-schema}

This appendix documents the canonical PostgreSQL schema of the platform.
The complete DDL is maintained in
\texttt{supabase/migrations/00000000000000\_schema.sql} in the project
repository and is the single source of truth for both the production Supabase
instance and any fresh development database. It consolidates 19 enumerated
types and 33 tables together with their triggers, indexes and foreign-key
constraints. Row-Level Security is intentionally disabled on every application
table; all database access is performed server-side through the service-role
key, as discussed in \secref{sec:design-security}.

\secref{app:db-enums} lists all enumerated types; \secref{app:db-candidates} shows the central \texttt{candidates} table in full as a representative example of the schema conventions; \secref{app:db-tables} lists the remaining 32 tables with their purpose.

\section{Central Table: \texttt{candidates}}
\label{app:db-candidates}

The \texttt{candidates} table is the hub of the schema. It links to
Supabase Auth via \texttt{user\_id}, holds all parsed CV fields, scoring
outputs, status lifecycle, and the GDPR-relevant invitation and
activation timestamps.

\begin{lstlisting}[language=SQL,
    basicstyle=\ttfamily\footnotesize,
    caption={The \texttt{candidates} table (central hub of the schema).},
    label={lst:candidates-table}]
CREATE TABLE candidates (
  id                       TEXT PRIMARY KEY,
  created_at               TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at               TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  user_id                  UUID REFERENCES auth.users(id) ON DELETE SET NULL,
  first_name               TEXT NOT NULL,
  last_name                TEXT NOT NULL,
  email                    TEXT UNIQUE,
  phone                    TEXT,
  location                 TEXT,
  country                  TEXT,
  linkedin_url             TEXT,
  date_of_birth            TIMESTAMPTZ,
  nationality              TEXT,
  willing_to_relocate      BOOLEAN,
  availability             TEXT,
  work_model               work_model,
  bio                      TEXT,
  raw_cv_url               TEXT,
  raw_cv_text              TEXT,
  parsed_data              JSONB,
  motivation_letter_url    TEXT,
  motivation_letter_text   TEXT,
  learning_agreement_url   TEXT,
  overall_cv_score         FLOAT,
  experience_score         FLOAT,
  education_score          FLOAT,
  location_score           FLOAT,
  language_score           FLOAT,
  years_of_experience      FLOAT,
  primary_business_area    TEXT,
  secondary_business_areas TEXT[]  NOT NULL DEFAULT '{}',
  parsing_confidence       JSONB,
  needs_review             BOOLEAN,
  status                   candidate_status NOT NULL DEFAULT 'NEW',
  source_type              candidate_source NOT NULL DEFAULT 'EXTERNAL',
  is_duplicate             BOOLEAN NOT NULL DEFAULT FALSE,
  duplicate_of             TEXT,
  secondary_email          TEXT,
  activated_at             TIMESTAMPTZ,
  invitation_sent          BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE TRIGGER trg_candidates_updated_at
  BEFORE UPDATE ON candidates
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE INDEX idx_candidates_email            ON candidates(email);
CREATE INDEX idx_candidates_status           ON candidates(status);
CREATE INDEX idx_candidates_overall_cv_score ON candidates(overall_cv_score);
CREATE INDEX idx_candidates_country          ON candidates(country);
\end{lstlisting}

Deduplication queries the \texttt{email} index for the high-confidence exact
match and the name and \texttt{location} columns for the weaker tiers
(\secref{sec:impl-cv}). One limitation of the current schema is that the
name comparison is accent-sensitive: PostgreSQL treats \texttt{Jo\~ao} and
\texttt{Joao} as distinct strings, so the same candidate recorded with and
without diacritics can slip past the name tiers. Making this robust would
require enabling the PostgreSQL \texttt{unaccent} extension and adding an
expression index over the accent-folded name (for example
\texttt{CREATE INDEX \dots\ ON candidates(unaccent(lower(first\_name)))}), so
the comparison runs against a normalised form on both sides. This is recorded
as future work.

\chapter{Implementation}
\label{cap:implementation}

This chapter describes how the design of \chapref{cap:design} was built.
It states the technology stack and its rationale, the layout of the
codebase, and then walks through the principal modules of TalentHub --- the
talent pool, the CV parsing pipeline, jobs and matching, the AI interviewer
integration, notifications, analytics, authentication and observability ---
before covering the continuous-integration pipeline and a small set of
representative code excerpts.

\section{Technology Stack}
\label{sec:impl-stack}

Every technology was weighed against five criteria: fitness for purpose,
developer experience, type-safety integration with TypeScript, compatibility
with Vercel's serverless runtime, and the ability to run on free or student
tiers. The stack deliberately avoids heavyweight enterprise infrastructure
(Kubernetes, message queues, microservices) in favour of a right-sized
single application built on Next.js \parencite{NextjsDocs}, TypeScript
\parencite{Bierman2014TypeScript} and Supabase \parencite{SupabaseDocs}.

The single most consequential choice was using \textbf{one framework for
both frontend and backend}, which removes a separate server, shared-type
generation and CORS handling. The alternatives --- a separate React/Express
backend, Angular/NestJS, Vue/Fastify or Remix --- were rejected as either
duplicative or a poor fit for the component ecosystem and the deployment
target. The other structural choices behind this stack --- the move to
Supabase over a separate ORM/database/storage/auth assembly, the deliberate
absence of an ORM, and the primary-with-fallback LLM provider strategy --- are
recorded with the alternatives weighed and the trade-off accepted in each case
in the design decision log (\secref{sec:design-decisions},
\tabref{tab:design-decisions}).

\section{CV Parsing Pipeline}
\label{sec:impl-cv}

CV ingestion is the most complex feature and is implemented as a nine-stage
pipeline with two entry points --- candidate self-upload (a single file) and
HR bulk upload (many files or a ZIP archive). The stages are: (1) validate the
file's MIME type and size; (2) store the original in Supabase Storage; (3)
extract text (\texttt{unpdf} for PDF, \texttt{mammoth} for DOCX, direct
decoding for plain text); (4) validate that enough text was recovered; (5)
send the text to the LLM with a structured-output prompt; (6) validate the
model's JSON against a strict Zod schema, retrying once on failure; (7) run
deduplication against existing candidates; (8) upsert the candidate and its
experiences, education, languages and skills; and (9) compute the CV score.

The prompt instructs the model to return a single JSON object with personal
information, experiences (each with a job title, company, dates, current-role
flag and a field-of-work tag), education, self-declared language levels and
categorised skills, using the provider's JSON mode. Two failure modes
dominate and are handled explicitly: \textbf{schema drift}, where the model
returns slightly malformed or invented fields --- absorbed by the schema's
tolerant coercion rather than a hard rejection --- and \textbf{provider rate limits or
outages}, absorbed by retrying the same request against the fallback provider.
A telemetry row is written per extraction for observability. For bulk
uploads, a \texttt{parsing\_jobs} row tracks parsed, failed and total counts
so that HR can monitor progress by polling; any per-file failures are
recorded in an \texttt{error\_log} array (filename and error message per
entry) and surfaced in the upload UI as an expandable list, without
aborting the rest of the batch.

The deduplication stage (step seven) deserves a closer look because the same
person frequently re-applies across campaigns, and silently creating a
duplicate record would corrupt every downstream count and ranking. The check
is tiered by confidence. An exact e-mail match is treated as the same person
with full confidence and merges into the existing record; a match on first
name, last name and location is treated as a probable duplicate (merged but
flagged for human review); and a match on name alone is treated as a weak
signal --- a new record is created but linked to the potential duplicate so a
recruiter can resolve it later. One known limitation of the name-based tiers
is that the comparison is currently accent-sensitive, so spellings that differ
only in diacritics (for example \emph{Jo\~ao} versus \emph{Joao}) are not
recognised as the same person; closing this gap requires accent-insensitive
matching at the database level, as noted in
\appref{app:db-candidates}. On a confirmed merge the candidate's related
records (experiences, education, languages and skills) are replaced wholesale
in a single operation rather than appended, so re-uploading an updated CV
refreshes the profile instead of accumulating stale rows. Bulk processing
runs asynchronously through the Next.js \texttt{after()} primitive: the route
returns \texttt{202\,Accepted} with a parsing-job identifier immediately, then
processes files in the background with a short throttle between LLM calls and
a cancellation check, and a stale-job recovery step marks any job left
processing for more than ten minutes as failed.

\subsection{Parse Confidence and Human-Review Triage}
\label{sec:impl-cv-confidence}

Automated extraction is never perfect, and the failure that matters is the
\emph{silent} one: a CV that parses into a plausible-looking record with the
wrong name, a dropped e-mail or mis-attributed dates pollutes deduplication,
search and every downstream score without anyone noticing. The pipeline
therefore attaches a \textbf{parse-confidence} object to every extraction, fed
by two complementary signals.

The first is the model's own self-assessment. The structured-output prompt
asks the model to return, alongside the extracted fields, an
\texttt{overall} confidence in $[0,1]$, per-field confidences (name,
location, languages, experience dates) and a list of free-text
\texttt{flags} such as \texttt{location\_uncertain}, \texttt{date\_gaps} or
\texttt{missing\_language\_levels}. This is cheap --- it costs only a few
extra output tokens --- and it surfaces uncertainties the model is
internally aware of. It is shown to the recruiter on the candidate profile
as a single ``parse confidence'' percentage with the flags listed beside it,
so the reviewer immediately knows which records to scrutinise.

It is important to be precise about what this number is and is not. It is the
model's \emph{stated} confidence, not a calibrated probability of
correctness: Large Language Models are known to be imperfectly calibrated and
can be confidently wrong. The value is therefore treated as a triage
heuristic, not a guarantee. To avoid relying on it alone, the pipeline adds a
second, deterministic signal: a rule-based check that forces review whenever a
critical identity field falls back to a placeholder --- a name that resolved
to \texttt{Unknown} or an e-mail that failed validation and became null.
These conditions raise their own flags (\texttt{name\_missing},
\texttt{no\_email}) regardless of what the model reported about itself.

A record is marked \texttt{needs\_review} when either signal fires --- the
model's overall confidence falls below a $0.7$ threshold, \emph{or} a
deterministic identity check fails. The philosophy is deliberately a
\emph{loud failure}: it is far better to flag a questionable parse for a few
seconds of HR attention than to write a confident-looking but wrong record
into the talent pool, where it would silently distort counts and rankings for
the rest of the candidate's lifecycle. The confidence object is persisted as
JSONB on the candidate row, so the triage signal travels with the record and
can drive a review queue.

\subsection{Parsing Cost and Scalability}
\label{sec:impl-cv-cost}

Because every CV and every job description is parsed by a Large Language
Model, the recurring cost of the platform is dominated by parsing tokens
rather than by hosting --- the database, storage and serverless functions all
sit comfortably inside free tiers at the volumes a single HR team generates.
It is therefore worth estimating how the parsing bill scales, and how the
choice of provider changes it. The estimate below is deliberately scoped to
\emph{parsing} (CV ingestion and job-description extraction); the AI
Interviewer is a separate service and is excluded.

A single CV parse is one LLM call. Measured against the telemetry rows the
pipeline records, a representative call carries roughly 1{,}800 input
tokens (the structured-output system prompt plus a one-to-two-page CV) and
returns roughly 900 output tokens of JSON. Job-description extraction is
comparable but slightly cheaper and far less frequent, so CV volume is the
right unit to reason about. \tabref{tab:parse-cost} turns that token profile
into per-CV and bulk costs across three small/fast models, and
\figref{fig:parse-cost} plots how the total scales as the number of parsed
CVs grows.

Three conclusions follow. First, at any realistic single-team volume the
parsing cost is small in absolute terms: even one hundred thousand CVs ---
far beyond a year of one recruiter's intake --- costs on the order of a few
hundred dollars on the primary model, and under a hundred on GPT-4o-mini.
Second, the slopes diverge sharply with scale, so provider choice is a
genuine architectural lever rather than a rounding error once the platform is
shared across teams or sites. Third, the Groq-primary / OpenAI-fallback design
(\secref{sec:concl-ai}) is defensible on cost as well as reliability. The
primary sits firmly in the low-cost band: as \tabref{tab:parse-cost} shows,
GPT-4o-mini is in fact marginally cheaper per CV, but Groq was chosen for its
generous free tier and high throughput, which keep both options negligible at
single-team volume. The fallback deliberately uses the larger GPT-4o ---
markedly more expensive per token --- but it is engaged only when the primary
is rate-limited or unavailable, so the platform bounds its worst-case cost
rather than paying that premium continuously.

Cost is only one axis of scalability; wall-clock time is the other. Because
bulk uploads are processed serially in the background task of
\secref{sec:impl-cv} and each CV takes roughly five seconds end-to-end, a
single run within the ten-minute stale-job window handles on the order of
100--120 CVs --- enough for a recruiter's realistic intake, but short of the
500-file batch cap, which very large imports must therefore split across
batches or offload to a durable queue (recorded as future work in
\chapref{cap:conclusions}).

\section{CV Scoring Engine}
\label{sec:impl-scoring}

Once a CV is parsed, the candidate receives a deterministic quality score.
The engine is a pure domain service: the same input always produces the same
output --- a property we adopted as a deliberate design principle of
transparency and reproducibility. The overall score is a weighted sum of five components, each
normalised to the range $0$--$100$, as set out in
\tabref{tab:cv-scoring}. Language proficiency carries the largest weight of any
single criterion ($35\%$), reflecting the platform's purpose as a
language-verification layer. Two of the components touch professional
experience from different angles: the $25\%$ \emph{Experience} weight stands
in for role-relevant experience --- only meaningful once a specific job is in
play, where the job-anchored fit (\secref{sec:impl-jobs}) replaces it with
\gls{llm}-assessed relevance --- while the $10\%$ \emph{Years of experience}
weight rewards raw tenure. In the generic, job-agnostic score the former is
proxied by the latter, which is why the worked example below scores both
alike. The two remaining components --- formal education and geographic
location --- each contribute $15\%$, completing the five-way split set out
in \tabref{tab:cv-scoring}.

\begin{table}[ht]
\centering
\caption[CV scoring components]{Components of the deterministic CV quality score.}
\label{tab:cv-scoring}
\small
\begin{tabular}{p{0.22\linewidth}p{0.10\linewidth}p{0.56\linewidth}}
\toprule
\textbf{Component} & \textbf{Weight} & \textbf{Calculation} \\
\midrule
Languages & 35\% & English proficiency in points (C2 35, C1 30, B2 20, B1 10, A2 5, A1 2), plus a Portuguese bonus (C2 25 down to A1 2) and $+10$ for each additional language at B2 or above (capped at $+30$); the total is clamped to $0$--$100$. A foreign candidate with no English is penalised and flagged for review. \\
Experience & 25\% & In the generic CV score this is proxied by years of experience; the job-anchored fit (\secref{sec:impl-jobs}) replaces it with LLM-assessed relevance to a specific role. \\
Education level & 15\% & Lookup: PhD 100, master 80, bachelor 60, vocational 40, high school 20, other 30 \\
Location match & 15\% & Distance from the adidas Porto site (Maia): same city $\approx 100$, decaying with distance to a floor of 10 within Portugal and Spain, and 0 outside that region \\
Years of experience & 10\% & $\min(100, (\text{years}/10)\times 100)$ --- ten years counts as full marks \\
\bottomrule
\end{tabular}
\end{table}

The formula is $\text{overall} = \sum_i (\text{component}_i \times w_i)$. A
candidate with seven years of experience, a master's degree, based in Porto
and fluent in English (C1) and Portuguese (C2) --- a language score of $55$ ---
therefore scores
$70\times0.25 + 70\times0.10 + 80\times0.15 + 100\times0.15 + 55\times0.35
\approx 71$, while a one-year bachelor in a different city with only basic
English scores roughly $16$ --- a spread that separates the pool without ever
obscuring how it was produced. A candidate whose overall score falls inside
the $45$--$60$ band is flagged as \emph{borderline}, marking them as close to
the threshold and a natural candidate for an improvement track.

One simplification here is deliberate: location distance is measured from a
single fixed origin, a choice whose rationale and the point at which it becomes
a real limitation are examined in \secref{sec:concl-partial}.

The same weighted-sum approach scores the language assessment, averaging the
three CEFR sub-scores (grammar, vocabulary and fluency) at equal weight, and a
banded lookup maps the resulting number onto
a CEFR level (for instance, $\geq 78$ maps to C1 and $\geq 65$ to B2). Both
the component weights and the assessment weights are domain value objects
(\secref{sec:design-domain}) and are persisted in editable
\texttt{scoring\_weights} and \texttt{scoring\_presets} tables, so a recruiter
can retune the model without a code change.

\section{Jobs and Matching}
\label{sec:impl-jobs}

Jobs are created and edited by HR or ingested by a scraper that collects
real listings from the adidas careers portal (used to populate a realistic
demonstration dataset). Because a full portal sync can take about a minute, it
reuses the same fire-and-forget pattern as the bulk CV upload
(\secref{sec:impl-cv}): the route returns \texttt{202\,Accepted} with a
sync identifier and runs the scrape through the Next.js \texttt{after()}
primitive, recording progress in a \texttt{sync\_jobs} row that the client
polls. The work therefore continues server-side regardless of the browser, so
the recruiter can navigate away and return to find the sync still progressing
or its result waiting. The same run also reconciles the local board against
the portal: scraped jobs that are no longer listed are marked closed, while
manually-created jobs are left untouched.

Because this trigger is available to any authenticated user rather than to HR
alone, overlapping sync requests are made safe on two independent levels.
\emph{At the request level}, the route is single-flight: before starting it
checks the \texttt{sync\_jobs} table for a run already in progress and returns
that one instead of launching a second, so concurrent clicks converge on a
single background job --- and a run stuck for more than five minutes is
auto-expired so the trigger can never wedge permanently. \emph{At the data
level}, the write itself is idempotent: scraped listings are upserted on the
unique \texttt{external\_id} key, so even two overlapping scrapes can only
converge on the same rows rather than create duplicates, and the reconciliation
that closes vanished listings is a no-op when repeated. Because the job board
is a single shared resource rather than per-user state, two recruiters --- or a
candidate and a recruiter --- refreshing at once is indistinguishable from one.

When an HR user first opens a job's
ranking screen,
its description is parsed lazily into the versioned requirements schema and
cached. The orchestrator \texttt{matchCandidatesToJob} then runs the matching
flow designed in \secref{sec:design-matching} (\figref{fig:match-flow}) ---
loading the candidate pool, running the pure \texttt{computeJobFit} for each,
and persisting the top results into the \texttt{job\_matches} cache. The \texttt{match-candidates} screen renders
the ranking with the per-criterion breakdown, and a per-job
\texttt{job\_shortlists} table records the recruiter's working pick list,
snapshotting the fit score at the moment a candidate is added so that later
re-ranking does not rewrite history.

A subtle defect in the bridge that converts a persisted database row into the
matcher's input type --- and the regression suite that now locks it down --- is
discussed with the testing lesson in \chapref{cap:validation}.

\section{AI Interviewer Integration}
\label{sec:impl-interviewer}

The conversational interviewer itself is the second team member's contribution
(\secref{sec:team}); this section documents only the integration surface owned
by the Next.js application, whose token-and-session contract with the sidecar is
described in \secref{sec:design-interviewer} and not repeated here. In
implementation terms that surface is a small set of API routes: one creates the
\texttt{interview\_sessions} row and issues the signed session token, a realtime
turn endpoint records each transcript turn, a proctoring endpoint logs integrity
events, and a results endpoint saves the structured evaluation returned by the
sidecar as the assessment result. Two details are specific to the
implementation. First, the selected skill (for the technical mode) is persisted
on the session and enforced server-side so that questions cannot drift off the
chosen topic. Second, the token-signing utility resolves its secret at call time
rather than at module load, so that a local build can complete without the
deployment-only secret while still failing fast at request time in production.

\section{Notifications and Campaigns}
\label{sec:impl-notifications}

The notification system serves both roles. It records pipeline events
(status changes, contact emails, promotional outreach) as typed
notifications, each carrying a metadata payload and the HR sender where
applicable. A per-candidate interaction-history panel reconstructs the full
timeline --- status changes, emails (with expandable bodies) and campaign
membership --- by joining notifications to their originating campaign or job.
Promotional campaigns are authored in a rich-text editor and fan out to
preference-aware recipients, respecting each candidate's field and country
notification preferences so that irrelevant outreach is suppressed.

\section{Analytics}
\label{sec:impl-analytics}

The analytics dashboard combines seven built-in charts (pipeline funnel,
status distribution, top skills and languages, trends and so on) with a
constrained custom-widget builder. Rather than exposing free-form SQL, the
builder is driven by a Zod-validated catalogue that whitelists the available
metrics, the dimensions allowed per metric, the chart types allowed per
dimension family, and the permitted filter keys; a strict widget-specification
schema rejects any unknown key. A hand-written query service runs each
validated specification, and a single universal renderer turns the resulting
\texttt{\{label, value\}} series into a bar, line, area, pie or stat chart.
Saved widgets are stored per user. This design gives HR analytical freedom
while making it impossible to express an injected or malformed query
(\chapref{cap:validation}).

artefact. A \emph{User guide} entry in the sidebar opens a role-aware help
dialog that renders a curated guide for the HR manager or the candidate,
selected from the same role context that drives the navigation, so a user can
jump straight to a feature and learn it without leaving the page they are
working on. Living next to the running application, the guide stays consistent
with the deployed feature set and reinforces the same role boundaries enforced
by the middleware (\secref{sec:impl-auth}).

\paragraph{Ambassador programs.}
HR can publish brand-ambassador programs (with a cohort, deadline, location,
requirements and perks) that candidates browse and apply to from their portal.
A submitted application is recorded against the program and the candidate is
idempotently tagged \texttt{brand-ambassador}, so the engagement campaign and
the talent pool stay in sync. Programs move through a draft/open/closed
lifecycle and applications through a submitted/under-review/accepted/rejected
flow.

\paragraph{Improvement tracks.}
When an assessment ends in a failing decision, the system auto-creates an

\paragraph{Candidate segments.}

the preference-aware campaign targeting described above, letting a campaign

profile, CV upload, applications and assessments.

\paragraph{Candidate self-service.}
The portal implements the full candidate journey of the use-case model
(\secref{sec:analysis-usecases}). A candidate enters either on their own
initiative through Google sign-in or by accepting an HR invitation, and from
the settings view manages personal contact details and per-type notification
preferences. Beyond the CV, the candidate can upload and replace two further
documents through dedicated routes --- a motivation letter and, for Erasmus
internships, a learning agreement --- each stored in the same object-storage
bucket as the CV. Applications are submitted against jobs, internships and
ambassador programs, and their status is tracked back to the candidate as the
HR recruiter advances each one. Open positions are browsed from a live feed
synced from the adidas careers portal by a sync action --- available to any
signed-in user --- and backed by the scraper. Finally, a ``Danger Zone'' in the settings view lets the
candidate delete their CV alone or erase their entire record and all stored
documents in one operation, alongside a CSV export of their profile ---
operationalising the GDPR rights of access and erasure directly in the
product rather than through a manual back-office request.

\section{Authentication, Roles and Middleware}
\label{sec:impl-auth}

Authentication uses Supabase Google OAuth. On first sign-in, an auth callback
route assigns the user's role into \texttt{app\_metadata.role} using the
service-role key, making it immutable from the client. The Next.js middleware
runs on every request: it refreshes the session, returns \texttt{401} for
unauthenticated API callers, returns \texttt{403} for non-HR callers on the
HR-only API prefixes, and protects the dashboard routes. Keeping this logic
in one middleware --- rather than repeating it in every route handler --- means
a new route is gated by default and the check cannot be forgotten. Inside
route handlers that need it, a small \texttt{require-hr} helper performs the
same role check with the revocation-aware \texttt{getUser()} call.

\section{Logging and Observability}
\label{sec:impl-observability}

Structured logging is provided by an in-house \texttt{createLogger(scope)}
factory that replaced raw \texttt{console} calls across the API routes. It
emits scoped, structured records and redacts personally identifiable
information --- e-mail addresses and tokens are masked --- so that logs
shipped to the hosting platform do not leak candidate data, a property pinned
by the redaction tests of \chapref{cap:validation}. The CV and
job-description parsers additionally write per-call telemetry rows, giving a
queryable view of provider reliability, latency and token cost.

\section{Continuous Integration and Deployment}
\label{sec:impl-cicd}

Every change runs through GitHub Actions, which type-checks the codebase with
\texttt{tsc -{}-noEmit} and executes the full Vitest suite with coverage,
uploading the coverage report as an artefact; that same type-check is the
canonical local validation step (\secref{sec:val-static}). Deployment is handled by Vercel, which
builds with Turbopack and provisions a preview deployment per change, so the
live deployment is always the demonstrable product increment referred to in
\chapref{cap:analysis}. A repository policy (\texttt{legacy-peer-deps})
keeps installs reproducible by pinning peers explicitly where they are only
transitively required.

\section{Selected Code Excerpts}
\label{sec:impl-code}

Three short excerpts illustrate the patterns described above. The first is
the core of the matching engine: a pure function that scores only the
applicable, weighted criteria and computes eligibility as their conjunction.

\begin{lstlisting}[language=TypeScript,caption={The matching engine core (\texttt{computeJobFit}).},captionpos=b]
export function computeJobFit(job, candidate, config = DEFAULT_FIT_CONFIG) {
  const breakdown = [
    matchField(job, candidate),    matchExperience(job, candidate),
    matchSeniority(job, candidate), matchRequiredSkills(job, candidate, config),
    matchPreferredSkills(job, candidate), matchLanguages(job, candidate),
    matchEducation(job, candidate),
  ];
  const weights = config.criterionWeights ?? DEFAULT_CRITERION_WEIGHTS;
  // Only applicable criteria with a positive weight contribute.
  const contributing = breakdown.filter(
    (c) => c.applicable && (weights[c.key] ?? 0) > 0);
  const totalWeight = contributing.reduce((s, c) => s + (weights[c.key] ?? 0), 0);
  const overallScore = totalWeight === 0 ? 0 : Math.round(
    contributing.reduce((s, c) => s + c.score * (weights[c.key] ?? 0), 0)
      / totalWeight);
  const isEligible = contributing.every((c) => c.met);
  return { overallScore, isEligible, breakdown };
}
\end{lstlisting}

The fourth is the escaping helper referenced above: it removes the characters
PostgREST treats as structural separators inside a \texttt{.or()} list before
the value is interpolated, so a crafted search term cannot inject additional
filter branches.

\begin{lstlisting}[language=TypeScript,caption={The PostgREST \texttt{.or()} sanitiser (\texttt{escapeOrTerm}).},captionpos=b]
export function escapeOrTerm(value: string): string {
  // PostgREST treats , ( ) : as structural separators in a .or() list;
  // strip them so a term cannot inject extra OR-branches.
  return value
    .replace(/[,():"\\]/g, " ")
    .replace(/\s+/g, " ")
    .trim();
}
\end{lstlisting}

The fifth illustrates the casing boundary between the database and the
application: rows arrive in \texttt{snake\_case} and are converted to the
\texttt{camelCase} used throughout the code, recursing into related rows but
never into the opaque JSONB payloads, whose internal keys must be preserved
verbatim.

\begin{lstlisting}[language=TypeScript,caption={Snake-to-camel conversion at the database boundary (\texttt{camelizeKeys}, abridged).},captionpos=b]
export function camelizeKeys(obj) {
  const out = {};
  for (const [k, v] of Object.entries(obj)) {
    const ck = toCamel(k);                    // job_title -> jobTitle
    if (v === null) out[ck] = v;
    else if (isIsoDate(v)) out[ck] = new Date(v);
    else if (Array.isArray(v)) out[ck] = v.map(camelizeIfObject);
    // JSONB columns are opaque payloads -- never recurse into them.
    else if (typeof v === "object" && !JSONB_KEYS.has(ck)) out[ck] = camelizeKeys(v);
    else out[ck] = v;
  }
  return out;
}
\end{lstlisting}

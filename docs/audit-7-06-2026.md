## 3. Finalization Blockers (do these before calling it "done")

These are the items that, if left, would be defensible to flag in a code review or thesis defense. Ordered by priority.

### 3.1 🟠 Interview routes still bypass the architecture (prior #2)

Six routes write directly to Supabase, violating the onion rule documented in [INSTRUCTIONS.md](../INSTRUCTIONS.md):

- [interview/session/route.ts](../src/app/api/interview/session/route.ts) (lines 57, 78, 89)
- [interview/realtime/route.ts](../src/app/api/interview/realtime/route.ts) (lines 89, 172, 175)
- [interview/realtime/turn/route.ts](../src/app/api/interview/realtime/turn/route.ts) (lines 147, 180, 186, 209, 291)
- [interview/realtime/terminate/route.ts](../src/app/api/interview/realtime/terminate/route.ts) (lines 132, 164, 250)
- [interview/results/route.ts](../src/app/api/interview/results/route.ts) (line 24)
- [interview/proctoring/route.ts](../src/app/api/interview/proctoring/route.ts) (lines 43, 69)

**Why it matters for finalization**: This is the single most visible inconsistency. Every other subsystem goes through a use case + repository; this one doesn't. In an academic context where "Clean Architecture" is a selling point, a reviewer will find this.

**Two honest options given the 2-week budget**:
- **(A) Fix it properly** (~1 day): add `IInterviewSessionRepository` port + `SupabaseInterviewSessionRepository` adapter + `InterviewUseCases` (`createSession`, `recordTurn`, `terminate`, `logProctoring`, `saveResult`). Routes shrink to ~10-line shells. Wire in the container.
- **(B) Acknowledge it explicitly** (~30 min): if time is tight, document it as a *known, deliberate* exception in `INSTRUCTIONS.md` and the report ("the realtime interview path trades the repository layer for latency; refactor tracked as future work"). Honesty beats a silent violation.

**Recommendation**: Do (A) if you have a spare day — it's contained and well-understood. Otherwise (B).

### 3.2 🟠 Interview token replay window (prior #10) — security

HMAC tokens have a 10-minute TTL but no single-use guard. A captured token is replayable within the window.

**Fix** (~½ day): add `interview_sessions.token_used_at TIMESTAMPTZ`; set it on first use; reject reuse. Migration + one test.

**Finalization note**: This is the most legitimate *security* gap left. For an academic submission it's worth either fixing or explicitly noting as a known limitation with the mitigation described.

### 3.3 🟡 Manual end-to-end verification pass (highest ROI, do this regardless)

Automated tests mock the LLM and the DB. Nothing currently exercises the *real* deployed pipeline end-to-end. Before finalizing, walk through each journey on `https://adidas-pool.vercel.app` and record the result:

**Candidate**: sign in → upload CV → verify parse accuracy → edit/save → apply to a job → take a written assessment → take an AI interview (TTS/STT in Chrome) → check notifications.

**HR**: sign in → bulk-upload a ZIP of CVs → watch progress/cancel → rank candidates for a job → shortlist → contact email → analytics + custom widget → ambassador program CRUD.

Capture screenshots — they double as report evidence. This is the cheapest way to find the bugs that unit tests can't.

## 4. Accuracy Risk — The One Strategic Item

The platform's value proposition is **parsing + matching accuracy**, and that is exactly where the deepest latent risk lives. This is fully analyzed in [CV_PARSING_IMPROVEMENT_PLAN.md](CV_PARSING_IMPROVEMENT_PLAN.md) (expanded 2026-06-07 to cover JD parsing and matching).

For the **2-week window**, you cannot and should not attempt that whole plan. But two items there are cheap and disproportionately protect your demo's credibility:

1. **Skill-matching for technical roles (plan R22)** — today's synonym table is 9 groups of *soft skills* with **zero technical equivalence** (`python`≠`programming`, `sql`≠`database`). If your demo includes any engineering/Data role, qualified candidates will silently rank low. Even a hand-written technical synonym dictionary (½ day) materially improves demo results.
2. **A tiny golden matching fixture (plan R31)** — 3–5 `(JD, candidate) → expected eligibility` cases pinned in a test. Cheap insurance that a last-minute prompt tweak doesn't wreck rankings during finals week.

Everything else in that plan (OCR, queues, dedup hardening) is legitimately *future work* — name it as such in the report.
